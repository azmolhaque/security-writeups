Thesis

Why "fixed fast" and "not rewarded" were both correct

An administrative IAM interface sat exposed on the public internet on a Google-acquisition subdomain. The login accepted default credentials, then accepted any password, and the API behind it answered unauthenticated requests — a complete failure of the authentication layer.

Google's product team triaged it P2/S2 and decommissioned it nine days after accepting the report. The VRP reward panel, separately, awarded credit and no cash. Both calls were right — and the useful part of this writeup is explaining, at a mechanism level, exactly why they don't conflict.

"…not located within a Google application, but was instead the result of stale DNS records. Because the vulnerability did not affect a system under our direct operational control, it does not qualify for a monetary reward…" — VRP reward panel, decision rationale

Calibrating that gap — between how severe a finding looks and how severe it is — is the actual job, on both sides of a triage queue and on any security team.

Method

Finding this class on purpose

The asset didn't surface by luck. It came from a repeatable method aimed at the highest-yield corner of a large, acquisition-heavy scope: stale, un-migrated infrastructure from recently acquired companies.

  1. Enumerate the acquisition scope, not just the flagship. Google's own scope file classifies *.photomath.net at Tier 1. Acquisition subdomains are where integration debt lives.
  2. Expand passively. Certificate-transparency logs and historical DNS surface hosts like rip. that never appear in the product's own navigation.
  3. Resolve and fingerprint, then filter for migration tells. A users/roles admin panel, reachable over plain HTTP, with no identity-aware proxy in front of it, on an acquisition-tier domain — every one of those adjectives is a symptom of infrastructure inherited and never folded into the acquirer's perimeter.
Evidence

Two controls, both absent

The login (Bienvenue administrateur) took the default pair admin@photomath.net / admin — then took any password string. That moves it from weak credentials (CWE-1188) to broken authentication (CWE-287): the frontend performed no meaningful validation at all. The login was decorative.

A UI bypass is weak if the backend still enforces authorization on its own. So the question that separates a screenshot from a finding: does the API check auth independently? It did not.

Unauthenticated requestrip.photomath.net
# no auth headers, no session cookie
GET /api/roles HTTP/1.1

HTTP/1.1 200 OK
[]

$ curl -i -s -X OPTIONS "http://rip.photomath.net/api/roles"
HTTP/1.1 200 OK
Allow: POST,GET,HEAD,OPTIONS
Via: 1.1 google

An unauthenticated GET returned an empty array, not a 401/403; OPTIONS advertised the write-capable method set (POST) with no auth. Two independent controls — frontend authentication and backend authorization — were both absent on the same surface.

A full screen recording — a successful login with a random password landing on the authenticated Roles dashboard — is embedded in the complete writeup. Watch it there →

Scope of testing. I confirmed read reachability and the advertised method set. I did not issue writes, create roles, or modify any state. Demonstrating reachability was sufficient to prove the control failure — claiming the write path worked without exercising it would have been overclaiming; noting it was advertised is fact.

Root cause

Edge-fronted ≠ Google-operated

The host resolved behind Google's edge and returned Via: 1.1 google. It's tempting to read "traffic flows through Google's edge" as "this is a Google-operated production system." It isn't the same thing — and the difference is the entire finding.

A DNS record inherited from the acquisition still pointed at a deployment Photomath spun up before the acquisition and never decommissioned. It was an orphaned frontend — outside the identity-aware proxy, outside standard edge TLS policy — not an integrated Google service. French UI strings, a users works! placeholder, and an empty /api/roles mark it as a dev/sandbox build with no real users or records. The fix being "pull the DNS record" rather than "patch the app" confirms it: there was no owned application to patch. This is the standard shape of acquisition-integration risk — its root cause is inventory and hygiene, not a defect in the acquirer's code.

Calibration

What would have crossed the reward bar

Knowing precisely what was missing is more valuable than the finding itself. A P2/S2 "Fixed" is an engineering signal — worth cleaning up. It is not a reward signal — real risk in a system Google operates. Those are different questions with different answers. Any one of these would likely have changed the outcome, and each is a concrete next test, not a wish:

If I had proven…Why it crosses the bar
/api/roles returned real user records (actual PII, not [])Data exposure Google is responsible for — impact realized, not hypothetical.
POST /api/roles created a role that federated into an authenticated, Google-operated systemPrivilege escalation from a husk into production — a pivot proven, not assumed.
Shared cookie domain (.photomath.net) or OAuth redirect_uri with a live production appSession/token theft against real users — the classic dangling-subdomain chain.

None applied here: empty sandbox, no shared authentication surface, no reachable production pivot. In my appeal I leaned on a hypothetical brand/phishing vector — adjectives, not a new fact — and the panel correctly upheld the original decision. Recognizing that before escalating is exactly the calibration the second decision was testing for.

Work sample

What this demonstrates

Read as a work sample, the useful signals aren't the bug — they're how it was handled.

  • Targeted recon, not spray-and-pray — surfaced via the acquisition-tier scope file plus CT logs, a repeatable method for un-migrated infrastructure.
  • Two-layer control analysis — checked whether the backend enforced authorization independently of the login form, not just the UI.
  • Minimal-impact testing — confirmed reachability and the advertised write methods without issuing a single write or touching data.
  • Severity calibration under pressure — argued the finding accurately, conceded where my appeal was speculative, and agreed with the credit-only outcome once the evidence was clear.
  • Coordinated disclosure — reported through the vendor channel, waited for remediation, re-verified the fix, and published only after NXDOMAIN.
