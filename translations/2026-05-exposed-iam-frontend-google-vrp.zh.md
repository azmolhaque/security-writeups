## 我为什么写这篇

大多数漏洞赏金文章止步于「我找到了 X，这是赏金」。更有用的故事往往是这一落差：一个发现*看上去*有多严重与它*实际*有多严重之间的落差——因为正确判断这一落差才是真正的工作，无论在分级队列的哪一侧，还是在任何安全团队中。

这个发现表面看来是关键级：一个未经身份验证的管理级身份与访问管理（IAM）界面，暴露在公共互联网上，位于一处属于 Google 收购的域名。Google 的产品团队同意它值得修复（P2/S2）并迅速加以修复。VRP 奖励委员会则另行判定它不值得金钱奖励——在梳理完证据后，我认为他们的理由完全正确。

因此本文做两件事：解剖技术构造，并且——诚实地，且在*系统为何如此表现*的层面上——解释为何「快速修复」与「分文不付」都是正确的决定。后半部分正是我希望招聘经理去读的部分。

## 1. 发现——以及如何有意地找到这一类

该资产是 `rip.photomath.net`，一个与 Google 收购（Photomath）相关的子域名。它并非靠运气浮现；它出自一套可复现的方法，瞄准一个庞大、收购众多的范围中产出最高的角落——**近期被收购公司留下的、陈旧且未迁移的基础设施**：

1. **枚举收购范围，而不只是旗舰产品。** Google 自己的范围文件 `external_domains_acquisitions.asciipb` 按级别对收购域名分类。`*.photomath.net` 就在其中，归为一级。收购子域名正是集成债务的栖身之处。
2. **被动子域名扩展**（证书透明度日志 + 历史 DNS）会暴露出像 `rip.` 这样、从不出现在产品自身导航中的主机。
3. **解析并对每台主机做指纹识别**，再严格地按未迁移基础设施（而非加固的生产环境）的迹象过滤：

| 观察 | 如何确定 | 为何重要 |
|---|---|---|
| 提供一个管理 UI（`GestionUsersRolesFrontend`） | 直接在浏览器加载 | 一处用户/角色管理的特权界面 |
| **仅明文 HTTP；TLS 在 `:443` 失败** | HTTPS 握手上的 `unexpected eof` | 一台处于收购方标准 TLS 终止边缘策略之外的主机——一个迁移迹象（CWE-319） |
| **由 Google 基础设施前置** | `Via: 1.1 google` 头；解析得到 GCP IP | 经由 Google 边缘转发——但正如第 5 节所示，由边缘前置**不等于**由 Google 运营 |
| 非英文管理文案（`Bienvenue administrateur`）、占位文本（`users works!`） | UI 检查 | 源公司的构建，很可能是开发/沙箱，在收购中原样带入 |

应当让有经验的猎手停下来细看的模式：**一个用户/角色管理后台面板，可经明文 HTTP 访问，前面没有任何 SSO / 身份感知代理，位于收购级别的域名上。** 这些形容词无一不是某处基础设施的症状：被继承下来，却从未纳入收购方的安全边界。

## 2. 身份验证的弱点

登录界面（`Bienvenue administrateur`）接受了教科书式的默认组合：

```
email:    admin@photomath.net
password: admin
```

单是这一点就属于 CWE-1188（默认凭据）。但进一步探测揭示了更根本的问题：该门户对管理员账户接受*任意*密码字符串。这把它从「弱凭据」推向了 **CWE-287（失效的身份验证）**——前端根本没有对后端做任何有意义的凭据校验。登录只是装饰。

我刻意加以验证（用随机字符登录），而非想当然，因为「默认凭据可用」与「身份验证完全缺失」是不同的严重性，我只想主张我能证明的那一个。

**🎥 证据——用随机密码字符串成功登录，抵达已认证的 Roles 仪表盘（未剪辑的屏幕录像）：**

## 3. 其背后的 API 层

用垃圾密码登录会抵达完整的管理仪表盘——上述失效身份验证的可见结果：

![在没有有效凭据的情况下抵达的管理级 IAM 仪表盘](../images/rip-photomath-dashboard.png)

*在没有有效凭据的情况下抵达的 IAM 仪表盘（`/dashboard`）——「Welcome, administrator」、Roles/Users 管理侧栏、「New role」写入控件，以及没有真实记录（一个空沙箱）。*

如果后端仍独立执行授权，那么 UI 级绕过就是个弱发现。因此，把一张截图与一个真正发现区分开来的下一个问题是：**这个 UI 背后的 API 会自己校验身份验证吗？** 它不会。

```http
GET /api/roles HTTP/1.1
Host: rip.photomath.net
# no auth headers, no session cookie

HTTP/1.1 200 OK
[]
```

![未经身份验证的 GET /api/roles 以 200 返回 []](../images/rip-api-roles-unauth.png)

未经身份验证的 GET 返回一个空 JSON 数组，而非 `401`/`403`。未经身份验证的 `OPTIONS` 则声明了完整的可写方法集：

```console
$ curl -i -s -k -X OPTIONS "http://rip.photomath.net/api/roles"
HTTP/1.1 200 OK
Allow: POST,GET,HEAD,OPTIONS
Via: 1.1 google
```

![OPTIONS 返回 Allow: POST,GET,HEAD,OPTIONS 和 Via: 1.1 google](../images/rip-api-options-allow.png)

`Allow: POST,GET,HEAD,OPTIONS` 表明该端点在无需身份验证的情况下接受写入（`POST`）。在未映射路径上的 `404` 返回了 Spring Boot 的默认错误页：

![Spring Boot Whitelabel 错误页](../images/rip-spring-boot-whitelabel.png)

于是两道相互独立的控制——前端身份验证与后端授权——在同一处界面上皆告缺失。这是架构上有意思的部分，也是这个发现之所以*完整*的原因：我没有止步于「登录是假的」，而是证明了数据层本身就是敞开的。

> **复现（只读摘要）。**
> 1. 解析 `rip.photomath.net` 并以明文 HTTP 加载（`:443` 的 TLS 握手失败）——管理 UI（`GestionUsersRolesFrontend`）渲染出来。
> 2. 在 `Bienvenue administrateur` 登录处，用**任意**密码字符串提交 `admin@photomath.net` → 抵达 `/dashboard`。
> 3. `GET /api/roles`，**不带**任何 cookie 或认证头 → `200 OK`，正文 `[]`（而非 `401`/`403`）。
> 4. `OPTIONS /api/roles` → `Allow: POST,GET,HEAD,OPTIONS`——在无需认证的情况下声明写入方法。
>
> 未发起任何写入，也未创建或修改任何记录；步骤 3–4 在不执行写入路径的前提下证实了控制失效。

**测试范围。** 我确认了读取可达性与所声明的方法集。我**没有**发起写入、创建角色或修改任何状态。证明可达性已足以证实控制失效，而在此止步正是 safe-harbor（安全港）预期所要求的。在不实际执行的情况下声称写入路径*可用*属于夸大；指出它被*声明*则是事实。

## 4. 修复

Google 的处置迅速而利落：

- **在约 24 小时内受理**并转交负责的产品团队。
- **在受理九天后标记为已修复**——端点被下线，主机名开始返回 `NXDOMAIN`。我独立地重新核验了 `NXDOMAIN` 并回报。
- 内部定级为 **P2 / S2**。

![Google Issue Tracker status: Accepted (comment #5) and Marked as fixed (comment #6)](../images/rip-tracker-accepted-fixed.png)

*追踪器自身的状态更新——报告次日即受理，九天后标记为已修复。我保留 Google 的原始措辞并略去发件人地址。诚实校准一下：喜庆的「🎉 Nice catch!」是该项目**标准的受理模板**，而非个人夸奖；真正有分量的是 P2/S2 定级与已确认的修复。*

![rip.photomath.net 现在返回 DNS_PROBE_FINISHED_NXDOMAIN](../images/rip-nxdomain-fixed.png)

请注意它*如何*被修复：不是代码补丁，不是身份验证中间件的改动——记录被撤除，主机停止解析。这个细节正是奖励决定的全部关键，也是下一节的主题。

## 5. 根本原因，精确地说：由边缘前置 ≠ 由 Google 运营

这是大多数文章略过的部分，也是真正解释一切的部分。

`rip.photomath.net` 在 Google 边缘之后解析到某个地址，并返回 `Via: 1.1 google`。人们很容易——起初我也倾向如此——把「流量经过 Google 边缘」读成「这是一套由 Google 运营的生产系统」。**二者并不相同**，而这一差别正是整个发现：

- 一条**从收购中继承而来的 DNS 记录**，仍指向 Photomath 在收购前搭建、之后从未下线或迁移的一处部署。它是一个**孤立前端**，而非集成的 Google 服务。
- 因为它从未纳入收购方的边界，它处于**身份感知代理之外**（没有 BeyondCorp/SSO 关卡），也处于**标准边缘 TLS 策略之外**（明文 HTTP，`:443` 失败）。这些不是彼此独立的漏洞——它们都是同一个症状：*这台机器从未被带进围栏之内。*
- 该应用几乎可以肯定是一个**开发/沙箱构建**——法语界面文案、`users works!` 占位符，以及空的 `/api/roles`。其背后没有真实的用户、凭据或记录。
- 修复方式是**「撤除 DNS 记录」**而非**「给应用打补丁」**，这佐证了根本原因：根本没有可打补丁的自有、在运营的应用。该漏洞栖身于一个**仅仅经由 Google 基础设施解析的悬挂产物**之中。

这正是**收购集成风险**的典型形态：当一家公司被收购，其 DNS 区域、云项目和半遗忘的部署会按某个时间表迁移，而陈旧记录会在这段间隙里留存下来。找到并修复它们绝对值得——但它们的根本原因是*资产清点与卫生*，而非收购方应用代码中的缺陷。

## 6. 为何这被恰当地未予奖励——以及什么会改变这一点

写下「未经身份验证的管理员访问 + 失效的身份验证 + 暴露的写入 API，位于一处一级 Google 资产上」并称之为关键级，是很容易的。起初我也把它描绘得很重。但**严重性是对真正重要的系统与数据的已实现影响**，而奖励委员会的理由很精确（引用其决定）：

> *「……并不位于某个 Google 应用之内，而是过期 DNS 记录所致。由于该漏洞并未影响我们直接运营控制之下的系统，故不符合金钱奖励的条件……」*

有三点与那种戏剧化的解读相悖，且三点都直接源自第 5 节：

- **(a) 非生产。** 占位文本与空的 `/api/roles`——空沙箱之上暴露的管理面板是一个真切的卫生问题，而非数据泄露。
- **(b) 卫生问题，而非应用漏洞。** 修复是下线一个悬挂端点。VRP 奖励的是 Google 运营系统中的缺陷，而非碰巧经由其边缘解析的孤立产物。
- **(c) 我最强的影响主张是臆测的。** 在申诉中，我依赖了一个**品牌/钓鱼向量**——攻击者可能从认得这个可信界面的员工那里窃取凭据。那是一种*假设性的次生*影响，而非已证明的危害，只是形容词，而非新的事实。委员会重新考虑后维持了原判，恰当地。

### 决定结果的区分：严重性轨道 ≠ 奖励轨道

P2/S2 的**「已修复」**是一个*工程*信号——团队判断它值得清理。它并非*奖励*信号。产品团队为「这该不该清理？」而优化；奖励委员会为「这是否在我们运营的系统中暴露了真实风险？」而优化。这是两个不同的问题，答案也不同，把它们混为一谈是一种常见的早期错误——我在申诉中就犯了。

### 什么*才会*越过奖励门槛（有用的反事实）

确切知道缺了什么，比这个发现本身更有价值。以下任何**一项**都很可能改变结论——而每一项都是一次具体的下一步测试，而非空想：

| 倘若我曾证明…… | 为何越过门槛 |
|---|---|
| `/api/roles` 返回了**真实的用户记录**（真实 PII，而非 `[]`） | 由 Google 负责的数据暴露——影响已然实现，而非假设 |
| **写入路径**（`POST /api/roles`）创建的角色**联合进入了一套已认证、由 Google 运营的系统**（共享 SSO/会话） | 从一具空壳向生产环境的提权——已被证明的横移 |
| 该主机与某个*在线、已认证的*生产应用**共享 cookie 域**（`.photomath.net`）或 OAuth `redirect_uri` 白名单 | 针对真实用户的会话/令牌窃取——经典的悬挂子域名利用链 |

这里无一成立：空沙箱、没有共享的身份验证面、没有可抵达生产的横移点。在升级申诉*之前*就认清这一点，正是第二个决定所要考验的那种校准——也是我本可以保住自身可信度的地方。

## 7. 如果由我来防御

对一支安全团队而言，这个发现作为检测与防范的教训，比作为战功轶事更有用。若这片边界归我所有：

**检测**
- 对每个收购域名（`*.photomath.net` 及同类）进行**持续的证书透明度监控**——新出现的和被遗忘的主机都会出现在 CT 日志中。
- 对收购级别范围文件中的每个子域名做**定期的解析并分类扫描**，标记出：明文 HTTP 的管理 UI、*不*在身份感知代理之后的主机，以及在未经认证的 `/api/*` 上出现的任何 `2xx`。
- **悬挂 DNS 对账**：将在线 DNS 区域与*有意运营*的部署清单相比对；任何无主而可解析之物，按定义就是一个发现。

**防范**
- 在 DNS 切换**之前**，把**所有**收购资产置于身份感知代理（BeyondCorp 式）之后，让未迁移的机器失败时是关闭而非敞开。
- 在**边缘强制仅用 HTTPS**并拒绝明文 HTTP——此处失败的 `:443` 本是一个免费的早期预警信号，却被忽视了。
- 把**收购的下线交接**当作清单项：按截止日期下线源公司的基础设施与记录，而非「以后再说」。

唯一能阻止整个暴露的控制，是身份感知代理：有了它，一个孤立的管理面板无论其自身身份验证多么失效，都是不可达的。

## 8. 我带走的经验

- **证明影响；不要从标签去推断。**「一级」描述的是一个域名的*潜在*敏感度，而非其上任一具体发现的严重性。真正重要的，是实际处于风险中的数据。
- **区分卫生问题与漏洞——在动笔之前。** 悬挂 DNS、沙箱暴露与陈旧端点常常是有效-但-仅致谢的。事先设定好这一预期，能让报告保持诚实、让申诉保持克制。
- **两层推理胜过一层。** 检查后端是否独立于登录表单执行身份验证——而不只看登录表单——正是让这个发现变得完整的原因。永远追问下一道控制在做什么。
- **申诉需要新的事实，而非更响的形容词。** 如果我无法补上具体的新证据，把措辞升级只会在分级人员面前损耗可信度。用更强的字眼重述影响，正是我的申诉没有（也不该）改变结论的原因。
- **由边缘前置，不等于由其运营。** 一个请求经由何处路由，丝毫不能说明谁承担风险。这一个区分，就是一个可获奖发现与一条卫生备注之间的差别。
- **校准才是那项技能。** 谁都能找到看上去骇人的东西。专业之举是精确陈述它到底有多重要——包括、尤其是当诚实的答案是「比初看时更轻」之时。

## 这个发现展示了什么

当作一份作品样本来读，这里真正有用的信号不是漏洞本身——而是它被如何处理的：

- **有的放矢的侦察，而非漫无目的**——经由收购级别的范围文件加 CT 日志浮现，是一套针对未迁移基础设施的可复现方法。
- **双层控制分析**——我检查了后端是否独立于登录表单执行授权，而不只看 UI。
- **最小影响测试**——我确认了可达性与所声明的写入方法，未发起任何一次写入，也未触碰任何数据。
- **压力之下的严重性校准**——我精确陈述该发现，承认申诉中臆测之处，并在证据清晰后接受仅致谢的结果。
- **协同披露**——经厂商渠道上报，等待修复，重新核验补丁（`NXDOMAIN`），仅在其后才发布。
