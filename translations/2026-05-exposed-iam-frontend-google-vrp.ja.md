## なぜこれを書くのか

たいていのバグバウンティの記事は「X を見つけた、これが報酬だ」で止まります。より有用な物語はたいてい、ある発見が*どれだけ深刻に見えるか*と*実際にどれだけ深刻か*の隔たりにあります——なぜなら、その隔たりを正しく見極めることこそが本当の仕事であり、それはトリアージ待ち行列のどちら側でも、どのセキュリティチームでも同じだからです。

この発見は表面上は重大に見えました——認証なしの管理用アイデンティティ・アクセス管理（IAM）インターフェースが、公開インターネットに露出し、Google の買収に属するドメイン上にありました。Google のプロダクトチームは修正に値すると同意し（P2/S2）、迅速に対処しました。VRP 報奨委員会は別途、それが金銭的報奨に値しないと判断しました——そして証拠を精査した結果、私は彼らの理由がまさに正しいと考えています。

そこで本稿は二つのことを行います——技術的な構造を解剖し、そして誠実に、かつ*なぜシステムがそのように振る舞ったのか*のレベルで、「早く直す」と「何も払わない」がともに正しい判断だった理由を説明します。後半こそ、採用担当者に読んでほしい部分です。

## 1. 発見——そしてこの種を意図して見つける方法

資産は `rip.photomath.net`、Google の買収（Photomath）に結びついたサブドメインでした。運任せで浮かび上がったのではありません——買収の多い広大なスコープの中でも最も実りある一角を狙う、再現可能な手法から得られたものです——**最近買収された企業の、古く未移行のインフラ**です。

1. **旗艦だけでなく、買収スコープを列挙する。** Google 自身のスコープファイル `external_domains_acquisitions.asciipb` は買収ドメインを Tier で分類します。`*.photomath.net` はそこに Tier 1 として載っています。買収サブドメインこそ、統合負債の潜む場所です。
2. **受動的なサブドメイン拡張**（証明書透明性ログ + 過去の DNS）は、製品自身のナビゲーションには決して現れない `rip.` のようなホストを浮かび上がらせます。
3. **各ホストを解決してフィンガープリントを取り**、そして硬化された本番ではなく未移行インフラの兆候で厳しく絞り込みます。

| 観察 | どう判定したか | なぜ重要か |
|---|---|---|
| 管理 UI（`GestionUsersRolesFrontend`）を配信していた | ブラウザで直接読み込み | ユーザー/ロール管理の特権的な面 |
| **平文 HTTP のみ；TLS は `:443` で失敗** | HTTPS ハンドシェイクでの `unexpected eof` | 買収側の標準的な TLS 終端エッジポリシーの外にあるホスト——移行の兆候（CWE-319） |
| **Google インフラによって前置** | `Via: 1.1 google` ヘッダー；解決時に GCP の IP | Google のエッジ経由でルーティングされる——が、第 5 節が示すとおり、エッジ前置は Google 運用と**同じではない** |
| 非英語の管理文言（`Bienvenue administrateur`）、プレースホルダ文言（`users works!`） | UI の検査 | 買収元企業のビルド、おそらく開発/サンドボックスが、買収でそのまま持ち越された |

経験ある狩人が立ち止まって注視すべきパターン——**ユーザー/ロールの管理者パネルが、平文 HTTP で到達可能で、前段に SSO / アイデンティティ認識プロキシもなく、買収ティアのドメイン上にある。** これらの形容詞のどれもが、継承されたまま買収側のセキュリティ境界に取り込まれなかったインフラの症状です。

## 2. 認証の弱点

ログイン画面（`Bienvenue administrateur`）は教科書どおりの既定の組み合わせを受け入れました。

```
email:    admin@photomath.net
password: admin
```

それだけで CWE-1188（デフォルト認証情報）です。しかしさらに探ると、より根本的なことが明らかになりました——ポータルは管理者アカウントに対して*任意の*パスワード文字列を受け入れたのです。これは「弱い認証情報」から **CWE-287（壊れた認証）** へと格を上げます——フロントエンドはバックエンドに対して意味のある認証情報の検証を一切行っていませんでした。ログインは飾りにすぎませんでした。

私はこれを推測ではなく意図的に確認しました（ランダムな文字でのログイン）。なぜなら「デフォルト認証情報が通る」と「認証が完全に欠如している」は異なる深刻度であり、証明できるものだけを主張したかったからです。

## 3. その背後の API 層

でたらめなパスワードでのログインは、完全な管理ダッシュボードに到達しました——上記の壊れた認証の可視的な結果です。

![有効な認証情報なしで到達した管理用 IAM ダッシュボード](../images/rip-photomath-dashboard.png)

*有効な認証情報なしで到達した IAM ダッシュボード（`/dashboard`）——「Welcome, administrator」、Roles/Users 管理サイドバー、「New role」書き込みコントロール、そして実レコードなし（空のサンドボックス）。*

バックエンドがなお独自に認可を強制しているなら、UI レベルのバイパスは弱い発見です。ゆえに、スクリーンショットと本当の発見を分ける次の問いはこうでした——**この UI の背後の API は認証を自ら検査するか？** していませんでした。

```http
GET /api/roles HTTP/1.1
Host: rip.photomath.net
# no auth headers, no session cookie

HTTP/1.1 200 OK
[]
```

![認証なしの GET /api/roles が 200 で [] を返す](../images/rip-api-roles-unauth.png)

認証なしの GET は `401`/`403` ではなく空の JSON 配列を返しました。認証なしの `OPTIONS` は、書き込み可能なメソッド集合の全体を広告しました。

```console
$ curl -i -s -k -X OPTIONS "http://rip.photomath.net/api/roles"
HTTP/1.1 200 OK
Allow: POST,GET,HEAD,OPTIONS
Via: 1.1 google
```

![OPTIONS が Allow: POST,GET,HEAD,OPTIONS と Via: 1.1 google を返す](../images/rip-api-options-allow.png)

`Allow: POST,GET,HEAD,OPTIONS` は、そのエンドポイントが認証なしで書き込み（`POST`）を受け付けることを示します。未マッピングのパスへの `404` は、Spring Boot の既定のエラーページを返しました。

![Spring Boot Whitelabel エラーページ](../images/rip-spring-boot-whitelabel.png)

こうして二つの独立した制御——フロントエンド認証とバックエンド認可——が、同一の面でいずれも不在でした。これがアーキテクチャ上興味深い部分であり、この発見が*完全*であった理由です——私は「ログインは張りぼてだ」で止めず、データ層そのものが開いていることを示しました。

> **再現（読み取り専用の要約）。**
> 1. `rip.photomath.net` を解決し、平文 HTTP で読み込む（`:443` は TLS ハンドシェイクで失敗）——管理 UI（`GestionUsersRolesFrontend`）が描画される。
> 2. `Bienvenue administrateur` のログインで、`admin@photomath.net` を**任意の**パスワード文字列とともに送信 → `/dashboard` に到達。
> 3. `GET /api/roles` を cookie も認証ヘッダーも**なし**で → `200 OK`、本文 `[]`（`401`/`403` ではない）。
> 4. `OPTIONS /api/roles` → `Allow: POST,GET,HEAD,OPTIONS`——認証なしで書き込みメソッドが広告される。
>
> 書き込みは一切行わず、レコードの作成・変更もしていません。手順 3–4 は書き込み経路を実行することなく制御の失敗を裏づけます。

**テストの範囲。** 私は読み取りの到達性と広告されたメソッド集合を確認しました。書き込みの実行、ロールの作成、いかなる状態の変更も**行っていません**。到達性を示すことで制御の失敗を証明するには十分であり、そこで止めることこそ safe-harbor（セーフハーバー）の期待が求めるところです。実際に行使せずに書き込み経路が*機能する*と主張するのは誇張であり、それが*広告されていた*と述べるのは事実です。

## 4. 修正

Google の対応は迅速かつ的確でした。

- **約 24 時間以内に受理**され、担当プロダクトチームに起票。
- **受理から九日後に「修正済」とマーク**——エンドポイントは停止され、ホスト名は `NXDOMAIN` を返し始めました。私は独立に `NXDOMAIN` を再検証し、報告し返しました。
- 内部的に **P2 / S2** と判定。

![rip.photomath.net は現在 DNS_PROBE_FINISHED_NXDOMAIN を返す](../images/rip-nxdomain-fixed.png)

*どのように*修正されたかに注目してください——コードのパッチでも、認証ミドルウェアの変更でもなく、レコードが引き抜かれ、ホストは解決しなくなりました。この一点が報奨判断のすべての鍵であり、次節の主題です。

## 5. 根本原因、正確に言えば：エッジ前置 ≠ Google 運用

これは多くの記事が飛ばす部分であり、実際にすべてを説明する部分です。

`rip.photomath.net` は Google のエッジの背後のアドレスに解決し、`Via: 1.1 google` を返していました。「トラフィックが Google のエッジを通る」を「これは Google が運用する本番システムだ」と読みたくなります——最初は私もそう傾きました。**両者は同じではなく**、その差こそが発見のすべてです。

- **買収から継承された DNS レコード**が、Photomath が買収前に立ち上げ、その後一度も停止も移行もしなかったデプロイをなお指していました。それは**孤立したフロントエンド**であり、統合された Google サービスではありませんでした。
- 買収側の境界に取り込まれなかったため、それは**アイデンティティ認識プロキシの外**（BeyondCorp/SSO のゲートなし）にあり、**標準のエッジ TLS ポリシーの外**（平文 HTTP、失敗した `:443`）にありました。これらは別々のバグではなく、すべて同じ症状です——*このマシンは一度も柵の内側に入れられなかった。*
- アプリケーションはほぼ確実に**開発/サンドボックスのビルド**でした——フランス語の UI 文字列、`users works!` というプレースホルダ、空の `/api/roles`。その背後に実ユーザー、認証情報、レコードはありませんでした。
- 修正が**「アプリのパッチ」ではなく「DNS レコードの引き抜き」**だったことが根本原因を裏づけます——パッチすべき自前の、運用中のアプリケーションは存在しなかったのです。脆弱性は、**Google のインフラを経由して解決されるだけの、宙ぶらりんの遺物**に宿っていました。

これは**買収統合リスク**の典型的な形です——企業が買収されると、その DNS ゾーン、クラウドプロジェクト、半ば忘れられたデプロイはある工程で移行され、古いレコードがその隙間に生き残ります。それらを見つけて直すことは間違いなく価値があります——しかしその根本原因は*棚卸しと衛生*であって、買収側のアプリケーションコードの欠陥ではありません。

## 6. なぜこれは正当に報われなかったのか——そして何がそれを変えたか

「認証なしの管理者アクセス + 壊れた認証 + 露出した書き込み API、Tier 1 の Google 資産上」と書いて重大と呼ぶのは簡単です。最初は私も強く枠づけました。しかし**深刻度とは、本当に重要なシステムとデータに対する実現した影響**であり、報奨委員会の理由は正確でした（その判断を引用します）。

> *「……Google のアプリケーション内に存在したのではなく、古い DNS レコードの結果でした。当該脆弱性は当社の直接的な運用管理下のシステムに影響しなかったため、金銭的報奨の対象にはなりません……」*

劇的な読みに反する三点があり、いずれも第 5 節から直接導かれます。

- **(a) 非本番。** プレースホルダ文言と空の `/api/roles`——空のサンドボックスの上に露出した管理パネルは、れっきとした衛生上の問題であって、データ侵害ではありません。
- **(b) 衛生であって、アプリの脆弱性ではない。** 修正は宙ぶらりんのエンドポイントを停止することでした。VRP は Google が運用するシステムの欠陥を報奨するのであって、たまたまそのエッジ経由で解決される孤立した遺物を報奨するのではありません。
- **(c) 私の最も強い影響の主張は憶測的だった。** 異議申し立てでは、**ブランド/フィッシングの筋**に依拠しました——攻撃者が、信頼された画面を見分ける従業員から認証情報を集めうる、というものです。それは*仮定的で二次的な*影響であり、実証された被害ではなく、新事実ではなく形容詞でした。委員会は再検討し、当初の判断を正当に維持しました。

### 結果を決めた区別：深刻度トラック ≠ 報奨トラック

P2/S2 の**「修正済」**は*エンジニアリング*の信号です——チームは片づける価値があると判断しました。それは*報奨*の信号では**ありません**。プロダクトチームは「これは片づけるべきか？」に最適化し、報奨委員会は「これは我々が運用するシステムに現実のリスクを露呈したか？」に最適化します。これらは別の問いで、答えも別です。そして両者を混同するのはよくある初期の誤りで——私は異議申し立てでそれを犯しました。

### 何が報奨のしきい値を*越えた*か（有用な反事実）

何が欠けていたのかを正確に知ることは、発見そのものより価値があります。以下のうち**どれか一つ**でも、おそらく結論を変えたでしょう——そしてどれもが具体的な次のテストであり、願望ではありません。

| もし私が証明していたら…… | なぜしきい値を越えるか |
|---|---|
| `/api/roles` が**実際のユーザーレコード**を返した（`[]` ではなく本物の PII） | Google が責任を負うデータ露出——実現した影響であって、仮定ではない |
| **書き込み経路**（`POST /api/roles`）が、**認証済みで Google が運用するシステムに連合するロール**を作成した（共有 SSO/セッション） | 空の抜け殻から本番への権限昇格——証明された横移動 |
| そのホストが*稼働中で認証済みの*本番アプリと **cookie ドメイン**（`.photomath.net`）または OAuth の `redirect_uri` 許可リストを共有していた | 実ユーザーに対するセッション/トークンの窃取——典型的なダングリング・サブドメインの連鎖 |

ここではどれも当てはまりませんでした——空のサンドボックス、共有された認証面なし、本番に到達できる横移動先なし。異議申し立てをエスカレートする*前に*それを認識することこそ、二つ目の判断が試していた較正であり、私が自らの信用を保てたはずの地点です。

## 7. 私が防御側だったら

この発見は、セキュリティチームにとって武勇伝としてよりも、検知と防止の教訓としてのほうが有用です。この境界が私のものなら——

**検知**
- すべての買収ドメイン（`*.photomath.net` とその同類）に対する**継続的な証明書透明性の監視**——新規のホストも忘れられたホストも、ともに CT ログに現れます。
- 買収ティアのスコープファイル内のすべてのサブドメインに対する**定期的な解決・分類スイープ**。平文 HTTP の管理 UI、アイデンティティ認識プロキシの背後に*ない*ホスト、認証なしの `/api/*` 上の任意の `2xx` を旗立てします。
- **ダングリング DNS の突合**——稼働中の DNS ゾーンを*意図して運用している*デプロイの棚卸しと突き合わせます。所有者なしに解決するものは、定義上すべて発見です。

**防止**
- DNS 切替えの**前に**、**すべての**買収資産をアイデンティティ認識プロキシ（BeyondCorp 式）の背後に置き、未移行のマシンが開いてではなく閉じて失敗するようにします。
- **エッジで HTTPS のみを強制**し、平文 HTTP を拒否します——ここで失敗した `:443` は無料の早期警告信号でしたが、見過ごされました。
- **買収のオフボーディング**をチェックリスト項目として扱います——買収元のインフラとレコードを、「いつか」ではなく期限までに停止します。

露出全体を防げたであろう唯一の制御は、アイデンティティ認識プロキシです——それがあれば、孤立した管理パネルは、その自前の認証がどれほど壊れていようと、到達不能です。

## 8. 持ち帰る教訓

- **影響を証明せよ。ラベルから推測するな。**「Tier 1」はドメインの*潜在的な*機微性を表すのであって、その上の特定の発見の深刻度ではありません。重要なのは、実際に危険にさらされているデータです。
- **衛生と脆弱性を区別せよ——書く前に。** ダングリング DNS、サンドボックスの露出、古いエンドポイントは、しばしば有効だが謝辞のみです。この期待を先に設定しておくことが、報告を誠実に、異議申し立てを規律あるものに保ちます。
- **二層の推論は一層に勝る。** バックエンドがログインフォームとは独立に認証を強制するかを確認したこと——フォームだけを見なかったこと——が、これを完全にしました。常に、その下の次の制御が何をしているかを問うことです。
- **異議申し立てには新事実が要る。より大きな声の形容詞ではない。** 具体的な新証拠を足せないなら、言葉を強めることはトリアージ担当者に対して信用を損なうだけです。影響をより強い言葉で言い直すことこそ、私の異議申し立てが結論を変えなかった（そして変えるべきでなかった）理由そのものです。
- **エッジ前置は、運用主体ではない。** リクエストがどこを経由するかは、誰がリスクを負うかを何も語りません。この一つの区別が、報奨に値する発見と衛生上の注記との差です。
- **較正こそが技能。** 誰でも警戒を誘うものは見つけられます。プロの一手は、それがどれほど重要かを正確に述べること——特に、誠実な答えが「最初に見えたほどではない」であるときにこそ、です。
